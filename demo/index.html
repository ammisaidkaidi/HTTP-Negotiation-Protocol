HTTP Negotiation Protocol — Web Demo

This page loads the real client library in the browser: the Authenticate button constructs a ClientAuthManager bound to a NegotiationClient and calls authenticate() directly against /auth — there is no /api/auth fetch endpoint. On the server, a ServerAuthManager is bound to a NegotiationServer on the same HTTP server. Demo account: user1 / correct-horse.

Auth workflow — every operation, live

Each step below is one operation of the auth negotiation. Press Authenticate and watch the steps change: pending → active → done (or failed). The page derives the live status from the real auth.* asks it receives and from the server registry returned by /api/state.

1

Browser creates the NegotiationClient

Browser — One NegotiationClient is created in the page. All later auth asks and normal calls go through this same client.

pending
2

Bind ClientAuthManager to the NegotiationClient

Browser — new ClientAuthManager(negotiationClient, { authUrl: "/auth", uid, password, timeBucketMs: 20000 }) registers the auth.* services and the Bearer-token plugin on that client.

pending
3

Begin the auth negotiation

ClientAuthManager → ServerAuthManager — clientAuth.authenticate({ force: true }) starts one logical negotiationClient.call("/auth", { begin: true }); the ServerAuthManager route starts one auth job.

pending
4

Time synchronisation — server asks auth.time

ServerAuthManager ⇄ auth.time service — Over several fast rounds the server asks auth.time; the client returns UTC epoch milliseconds. Using the fastest sample, the clocks must agree within 20,000 ms, otherwise the job fails with CLOCK_SKEW.

pending
5

Server requests the UID and resolves the password

ServerAuthManager ⇄ auth.getUid service — The server asks auth.getUid; the client sends its uid, and the server resolves the per-user password with its getPassword(uid) lookup. Unknown uid → UNKNOWN_UID.

pending
6

Server creates the encrypted challenge

ServerAuthManager — The server builds { data, challenge, nonce } (random data plus built-in function names such as double/square/xor42) and encrypts it with AES-256-GCM under a key derived by HKDF-SHA256 from the password and the UTC time bucket (time\20000), using Web Crypto.

pending
7

Client solves the challenge

auth.solveChallenge service — The client decrypts the envelope, applies the named pure functions f(x) => y in order, and returns { result, nonce } encrypted the same way.

pending
8

Server validates the encrypted answer

ServerAuthManager — The server decrypts the answer and compares the nonce and result with the expected value. Wrong password or a tampered answer fails here (DECRYPT_FAILED / CHALLENGE_FAILED).

pending
9

Token is generated

ServerAuthManager — Only after validation succeeds, the server generates the session token (random bytes from a fresh crypto.subtle.generateKey AES-GCM key, exported and base64url-encoded).

pending
10

Token is saved to the server registry FIRST

ServerAuthManager registry — The server does registry.set(token, entry) before the token leaves the server. That registry save is what marks the authentication as successful.

pending
11

Token is delivered and the client returns ack

ServerAuthManager ⇄ auth.acceptToken service — The server asks auth.acceptToken with the token; the client stores the session in memory and returns { ack: true }.

pending
12

Registry is marked acknowledged and the job ends

ServerAuthManager — After the ack, the server marks the registry entry acknowledged, returns { authenticated, uid, expiresAt, clockOffsetMs }, and the auth job/connection closes.

pending
13

Use the token — or close and re-authenticate

NegotiationClient — The bound client now sends authorization: Bearer <token> automatically (try “Call /whoami”). clientAuth.close() forgets the token, so the next authentication runs this whole workflow again and creates a new token.

pending
